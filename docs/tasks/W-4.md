# W-4 · Fix what the first Windows recording found

## Goal
A recording with screen, camera and microphone works on Windows from a fresh start, and what is left is listed.

## Read first
- `docs/tasks/W-3.md`
- `docs/WINDOWS-VERIFY.md`

## Files in scope
- Windows blocks in `src-tauri/src/`, the dshow / ddagrab paths in `src-tauri/crates/core/src/command.rs`
- `src-tauri/src/commands.rs` (shared: separate pull request)

## Done when
- [x] the picker opens and a recording starts
- [x] the camera is in the recording when it is switched on
- [x] audio and video of every segment have the same length (±100 ms)
- [x] the recording bar is not in the video
- [ ] the open items below are fixed or have their own card

## Human steps
- watch and listen to `win-verify-2.mp4`; clap once on camera to check that sound and picture are in step

## Result

Five defects fixed on 2026-11-11, each found in a real run of `npm run tauri dev`:

| # | What happened | Cause | Fix | Branch |
|---|---|---|---|---|
| 1 | The app froze as soon as the screen picker opened; every IPC call timed out | `show_screen_marker` was a synchronous command, so it built the marker window on the main thread, which deadlocks on Windows | the command is `async` | `shared/marker-window-deadlock` |
| 2 | The camera was dropped: log `start failed, trying with less`, ffmpeg `Could not run graph` | WebView2's Media Foundation capture kept the camera for 95–115 s after the self-view stopped; on Windows only one client gets a camera | the app starts its webviews with `MediaFoundationVideoCapture` disabled; release now takes under 1.2 s | `win/camera-handoff` |
| 3 | With the camera on, each segment's audio was 9.5 % shorter than its video; ffmpeg ran at 0.83× | the camera delivers 25 fps in low light but stamps frames 1/30 s apart; the overlay follows those stamps | `-use_wallclock_as_timestamps 1` on the dshow camera input, with a unit test | `win/camera-handoff` |
| 4 | The recording bar was in the video | ddagrab records every window | the floating window is excluded from capture (`set_content_protected`) | `win/camera-handoff` |
| 5 | An empty `.flowgt-recorder` folder was visible among the recordings | a leading dot hides nothing on Windows | the folder is marked hidden when a recording starts | `win/camera-handoff` |

Evidence, same machine, 45 s of screen + camera + microphone with the app's arguments:

## Open items (not fixed)

1. **WebView2 permission prompts.** "…wants to use your cameras / microphones" appears in the main window on
   first run, and in the recorded picture if it is still open. The app should answer it for its own origin
   (WebView2 `PermissionRequested`), which needs a Tauri-side hook. Done on `win/webview-permissions` for the app's own origin, camera and
   microphone only; verified with a fresh WebView2 profile. It removes a consent question, so it waits for
   Gabriel's decision.
2. **The marker window follows the router.** After a recording it navigates to `#/summary`
   (`App.svelte` only excludes `/floating`). Seen in the target list; what the user sees on the next picker
   was not checked. Shared file.
3. **Device matching in the webview.** WebView2 labels the camera `2K USB Camera (2bdf:0281)`; the app compares
   with the dshow name `2K USB Camera`, never matches and falls back to the default device. With two cameras
   the self-view can show the wrong one. Same for the microphone level meter.
4. **"Same as system" is the first dshow device**, not the Windows default. On the test machine the two
   happen to be the same microphone (Fifine), read from the audio endpoint API; the logic is still first-in-list.
5. **Non-ASCII device names**: no such device here; untested.
6. **Live preview panel** under the recording bar says "Waiting for the first frame…" for the whole
   recording: the ffmpeg path has no preview source. It should be hidden on Windows (capability flag, S-2).
7. **Screen picker thumbnail** is an empty grey box on Windows; the screen is called "Screen 1".
8. **Elapsed time** counts from the click; the file is 4–5 s shorter than the timer per segment start
   (device opening). `win-verify`: timer 2:47, file 2:40.
9. **`.flowgt-recorder`** stayed as a visible empty folder next to the recordings. Fixed on this branch: the
   recorder marks it hidden on Windows (attributes `Hidden, Directory` after one recording).
10. `scripts/bench.ps1` now uses the fetched sidecar (on `win/fetch-ffmpeg`) and still ends in FAIL on `h264_qsv` (501 MB/h on the test pattern);
    `hevc_mf` / `h264_mf` do not open with `-hw_encoding 1` here.
11. `--selftest` failed on Windows ("ffmpeg / ffprobe not found") and four supervisor tests were silently
    skipped. Fixed on `shared/encoder-probe`: the self-test exits 0 and the tests run (35 passed, 1 ignored).
12. **Audio and video end apart in short clips.** In the test matrix (16 short recordings, report 02, section 6)
    9 of the 14 clips with sound end 0.3–1.4 s apart, and the two clips with a pause and the camera have a 1.2 s
    and a 1.6 s hole in the audio at the pause. The two-minute run above does not show it. One cause is measured:
    the microphone arrives through dshow in 0.5 s blocks, and `-audio_buffer_size 50` does not change that
    (`docs/tasks/W-6.md`). Whether sound and picture are in step was not measured with a real signal.
13. **"Auto" keeps the last encoder.** After one H.264 recording, "Auto" recorded H.264 until a restart. Fix
    on `shared/encoder-cache-pref`.
14. 3840-wide output came out at 455 MB/h against the 400 target.

## Not verified

- Every fix was measured on one machine, one camera, one Windows build (26300, an Insider build). The 95 s
  camera hold may be specific to it.
- None of the changes was built on macOS. Fixes 2 and 4 are Windows-only code; fix 3 is in the dshow branch of
  the core; fix 1 changes a shared command from sync to async.
- Why ffmpeg holds about 870 MB during a recording. It is not the defect of fix 3: a 30-minute run after the
  fix stayed at 852–886 MB.
