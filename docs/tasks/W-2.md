# W-2 · Fetch LGPL ffmpeg for Windows

## Goal
One script puts LGPL `ffmpeg` and `ffprobe` for Windows into `src-tauri/binaries/` with the right names.

## Read first
- `scripts/fetch-ffmpeg.sh`
- `docs/LICENSES.md` → ffmpeg

## Files in scope
- `scripts/fetch-ffmpeg.ps1` (new)
- `scripts/integration.ps1`, `scripts/README.md` (rows for the two scripts)
- `docs/LICENSES.md`

## Done when
- [x] `ffmpeg -L` prints the LGPL; the configure line has no `--enable-gpl` / `--enable-nonfree`
- [x] `pwsh scripts/integration.ps1` passes with the fetched binaries

## Human steps
- none

## Result

Run on 2026-11-11, Windows 11 Pro build 26300, Intel Core Ultra 5 225 (integrated graphics), PowerShell 7.6.9
and Windows PowerShell 5.1.

**Order changed: W-2 had to come before W-1.** `cargo test --workspace` cannot build the app crate without the
sidecars; tauri-build stops with ``resource path `binaries\ffmpeg-x86_64-pc-windows-msvc.exe` doesn't exist``.
The dependency in the front matter is therefore removed, and W-1 now depends on this card.

`scripts/fetch-ffmpeg.ps1` downloads one pinned BtbN LGPL build, checks the archive SHA-256, checks the licence
of both tools **before** copying them, and is a no-op when the binaries are already there.


A second run under Windows PowerShell 5.1 printed `already present (use -Force to replace):`, the same two
hashes and `PASS`.

`scripts/integration.ps1` now prefers the fetched sidecars over `ffmpeg` on PATH and says which it used:

```
> pwsh -NoProfile -File scripts/integration.ps1
ffmpeg=src-tauri/binaries/ffmpeg-x86_64-pc-windows-msvc.exe ffprobe=src-tauri/binaries/ffprobe-x86_64-pc-windows-msvc.exe
[hevc_nvenc @ …] Cannot load nvcuda.dll
…
encoder hevc_nvenc failed, trying next
Incompatible pixel format 'yuv420p' for codec 'hevc_qsv', auto-selecting format 'nv12'
encoder=hevc_qsv duration=6 kbps=997 video=hevc audio=aac
PASS
```

The same command under Windows PowerShell 5.1 gave the same last two lines.

Findings for later cards:

1. **`hevc_nvenc` is listed by `-encoders` on a machine with no NVIDIA card** and fails when opened
   (`Cannot load nvcuda.dll`). The script falls through to `hevc_qsv`. The app picks encoders by name from the
   same listing (`encoders::choose`), so W-3 has to check that the app test-encodes before trusting a name.
2. **`-pix_fmt yuv420p` is not accepted by `hevc_qsv`**; ffmpeg switches to `nv12` with a warning. The file is
   still 4:2:0. Harmless here, to be confirmed in the app's own command line (W-3).
3. **997 kbps on the synthetic test pattern**, against the 889 kbps budget (the script fails only above 1100).
   Real screen content is measured in W-3.

## Not verified

- The `-FromDir` and `-Force` switches were not run.
- No ARM64 Windows: the script refuses anything but x64.
- The licence check reads `-L` and the configure line; nobody has read the build's full licence texts.
- This is an LGPL **version 3** build (`--enable-version3`). Whether a release may ship it is not decided
  (`docs/LICENSES.md`); the release checklist there is still open.
- The pinned URL depends on upstream keeping that autobuild release. No mirror, no archived source tarball.
