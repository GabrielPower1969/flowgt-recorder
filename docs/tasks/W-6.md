## Research notes (2026-11-11, plan only, nothing built)

Written after the first night of real recordings on Windows (`docs/tasks/W-3.md`, `W-4.md`). Evidence labels as
in `docs/PLATFORM-ARCHITECTURE.md`: **A** = measured or read tonight on the test machine, **D** = from memory of
the Windows APIs, not checked against Microsoft's pages tonight. Every D line must be checked before decision W2.

### Why the ffmpeg path is not enough (all A, from W-3 / W-4)

| What the ffmpeg path did on Windows | Consequence |
|---|---|
| Three inputs, three clocks (ddagrab, dshow camera, dshow microphone) | the camera clock ran at 25/30 and dragged the whole file; fixed by a workaround, not by design |
| dshow hands audio over in large blocks | audio and video end 0.3–1.4 s apart in 9 of the 14 short clips that had sound |
| The camera is exclusive: webview self-view and ffmpeg cannot share it | hand-over needs a webview flag; resume reopens every device (2.8 s) |
| No system audio without a loopback device | "Computer audio" is disabled on a stock Windows 11 PC |
| No window capture, no thumbnails, no live preview | picker shows a grey box; the preview panel says "Waiting for the first frame…" |
| Devices open after the click | the file is 4–5 s shorter than the timer at every start and resume |

This is the list D27 fixed on macOS with `sck-record`. The same cure fits.

### Recommendation

Build `helpers/win-record/` as **one Rust executable that speaks the `sck-record` protocol unchanged**: the same
arguments (`native::helper_args`), the same JSON events on stdout, `stop` on stdin, the same exit codes. Then
`recorder.rs` supervises it with the code that already supervises the macOS helper, and S-1's conformance test
runs against both.

| Part | API | Label |
|---|---|---|
| Screen and single window | Windows.Graphics.Capture: `GraphicsCaptureItem` for a monitor or an HWND, a free-threaded frame pool, cursor on or off | D |
| Leave the app's own windows out | already done for the ffmpeg path with `set_content_protected` (W-4); capture honours it | A for desktop duplication, D for Graphics.Capture |
| System audio | WASAPI loopback on the default render endpoint; process loopback that excludes the app's own process tree where the OS has it (build 20348 or later, per `PLATFORM-ARCHITECTURE.md`) | D |
| Microphone | WASAPI capture, shared mode, event driven | D |
| Camera | Media Foundation source reader; frames composed into the output on the GPU (Direct3D 11) as the rounded square | D |
| Encoder and file | Media Foundation sink writer with the hardware HEVC / H.264 transforms, AAC, fragmented MP4 | D |
| One clock | the performance counter stamps every video frame and audio block; frames are written on an output tick that takes the latest screen and camera frame, as `sck-record` does | design |
| Language | Rust with the `windows` crate: one toolchain with the shell, no C++ build | D (the crate's coverage of these APIs is not checked) |

Minimum Windows version to state in W2: Windows 10 for capture and loopback of the whole endpoint; newer builds
for borderless capture and per-process loopback. The exact build numbers are D and must be read off the
documentation.

### Prototype, in the order that removes risk first

1. `--list`: monitors and windows as JSON in the `sck-record` shape. Proves the crate and the picker data.
2. One monitor to a fragmented MP4 with the hardware encoder, 10 s, no audio. Proves the sink writer and the
   fragmented output that invariant 3 requires.
3. Add system audio (endpoint loopback) on the shared clock. Check with a beep-and-flash test that sound and
   picture are within 100 ms. This is the card's "done when".
4. One window instead of the monitor; move, resize, minimise and close it.
5. Microphone, then camera picture-in-picture, then `--preview`.

Steps 1–3 are the spike. Steps 4–5 are the engine itself and belong to a later card.

### Not solved, to be answered by the spike

- Whether a hardware HEVC encoder is present on ordinary PCs, and what the fallback is (H.264 hardware, then
  software). On the test machine ffmpeg's `hevc_mf` did not open with `-hw_encoding 1` while `hevc_qsv` did (A).
- Whether the Media Foundation camera path shows the same 95 s hold seen with WebView2 (A for WebView2 only).
- Protected content (video players), HDR screens, two GPUs, mixed scaling across monitors.
- Loopback is silent while nothing plays: the writer needs to insert silence so the track keeps its length.
- Size and startup time of the helper; code signing (W-7).

### Cheaper steps for the ffmpeg path in the meantime (not done)

- `-audio_buffer_size 50` on the dshow microphone input, to shrink the audio blocks. Untested.
- A 200-line WASAPI loopback helper that writes PCM to a pipe, used through the existing `PcmPipe` input the
  macOS audio helper already has. That is W-5's "small helper" option and would give system audio before the
  full engine exists.
