写报告的是 Windows 负责人的 agent（Claude Fable 5.2），在测试机上从 00:35 干到 04:35。凡是写“通过”“测得”的地方，

## 1. 一句话结论

Windows 版今晚第一次真的跑起来了：能装、能编、四项自动检查全绿，屏幕＋摄像头＋麦克风能录成一个 HEVC 1080p 的 MP4，
体积在每小时 400 MB 的预算内；途中发现并修掉了 8 个问题，其中 3 个会让它完全不能用或把录像录坏。**还不能说“可以给人用”**：
没有人看过、听过任何一段录像，音画是否同步没有用真实信号测过，电脑声音在这台机器上录不了，界面有一批不顺手的地方
（已画成新的设计稿，没有动代码）。

## 4. 没验证的东西

1. **没有人看过或听过任何录像。** 检查手段只有 ffprobe、完整解码一遍、抽帧看图、测音量。录音内容基本是安静房间里的静音（见第 6 节说明 3），
   所以“麦克风录得清不清楚”完全没有验证。
2. **音画是否同步没有用真实信号测。** 没有回环设备，夜里也没有放声音；我试过用到达时间估算起点偏移，实验没做成。只比了容器里的时间：
   14 段有声音的短录里，9 段的声音和画面结尾相差 0.3–1.4 秒（表见第 6 节）；带摄像头并暂停的两段，暂停处有 1.2 和 1.6 秒的音频缺口。
   两分钟那段没有这个问题；30 分钟那段没有缺口，但声音比画面早结束 1.3 秒。已查到一个原因：这支麦克风经 DirectShow 是每 0.5 秒交一块声音，
   `-audio_buffer_size 50` 也改不了（`docs/tasks/W-6.md`）。**这是目前最大的风险。**
3. 所有修复只在这一台机器、这一个摄像头、这一个 Windows 版本上测过。26300 是预览版系统，摄像头被占 95 秒可能是它特有的。
4. 没有任何一处改动在 macOS 上编译或运行过。#5 把一个共享命令从同步改成异步；#1、#2、#8、#11 改了共享代码；#13 改了共享契约和两个共享组件。
5. `shared/encoder-cache-pref` 在应用里只复测了“H.264 → 自动”这一种切换。
6. 界面自动化今晚很不顺，前后浪费了一个多小时，原因有三个，都出在我自己的做法上，不是应用的毛病：驱动脚本的超时定时器让每次调用空等 20 秒；
   我把一个独立工作副本放进了项目目录，开发服务器把它也当项目文件来监视；被我中止的走查脚本的子进程还活着，和新的一起操作应用。
   因此“应用在人手操作下顺不顺”这件事，今晚没有可靠的结论。
7. `shared/ci-sidecars` 完全没验证（CI 没跑）。
8. ffmpeg 在长录里稳定占约 870 MB。我一度以为这是摄像头时钟问题造成的，长录证明不是；真正原因没查（猜测是 4K 原始帧的排队缓冲）。
9. 托盘图标录制时有没有变、全局快捷键、Google 登录和上传、磁盘不足提示、恢复未完成的录像：都没测。
10. “跟随系统”选的是 ffmpeg 列出的第一个设备。这台机器上第一个麦克风恰好就是 Windows 的默认麦克风（Fifine），所以显示是对的，
    但逻辑没验证。
11. W-6 里标 D 的每一条 Windows API 说法都没有对照微软文档。
12. 设计稿里写的对比度是按 WCAG 公式算的，没有用屏幕取色核对；原型的倒计时一屏没截到图。
