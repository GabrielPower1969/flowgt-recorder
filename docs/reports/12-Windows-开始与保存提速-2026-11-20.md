# 12 · Windows：倒数结束就开录，点停止就保存

- 日期：2026-11-20，无人值守。作者：Claude（Windows 负责人）。分支 `win/faster-start-stop`（基于 `win/overnight-2026-11-13`，并带上了 Mac 的 #24 那一提交 `8098c28`，内容相同），草稿 PR。
- 证据在 `tests/out/startstop/`（git 忽略），下文文件名都相对这个目录。
- 测试机：Windows 11，Intel 核显，一块 4K 屏幕，USB 摄像头和 USB 麦克风。“旧版”和“新版”都是本机编的发布版，同一台机器、同一套脚本、前后紧挨着测。

## 1. 结论

| 场景（3 秒倒数，摄像头＋麦克风，除非另说） | 旧版 | 新版 |
|---|---|---|
| 倒数结束 → 进入录制 | 2011 ms | **−10 ms**（倒数结束那一刻） |
| 只开麦克风 | 1164 ms | −11 ms |
| 只录屏 | 895 ms | −6 ms |
| 点停止 → 文件存好（8 秒录像） | 795 ms | **250 ms** |
| 点停止 → 文件存好（5 分钟录像） | 1060 ms | 288 ms |
| 点停止 → 主窗口出来、显示保存进度 | 2 ms | 2 ms（Mac 的改动，Windows 上实测有效） |
| 倒数结束后丢掉的画面 | 911 ms | 0（文件正好从倒数结束开始） |
| 画面和声音的长度差（同步） | 0.917 s | **0.074 s** |
| 暂停 | 638 ms | 95 ms |
| 暂停后再停止 | 814 ms | 393 ms |
| 继续（暂停后） | 1819 ms | 1849 ms（没变，见 4.1） |
| 不倒数直接录 | 2037–2138 ms | 1946–1987 ms（基本没变，见 4.2） |

上架版（MSIX，我们自编的 ffmpeg＋QSV）只录屏：倒数结束 → 录制 −8 ms，停止 → 存好 213 ms，文件第一帧是关键帧 `[A · msix-screen.txt]`。

每一行都是中位数；摄像头＋麦克风 5 次，其他 3 次，长录像各 1 次。原始数据：`base-*.txt`（旧版）、`final-*.txt`（新版）、`flows-compare.txt`（暂停／取消／不倒数）。

## 2. 怎么测的

脚本已放进仓库，谁都能重测（Windows，Node 22 以上，先 `npm run tauri build`）：

```
powershell -ExecutionPolicy Bypass -File scripts/bench-app-win.ps1      # 带调试端口启动应用
node scripts/bench-start-stop.mjs cam-mic 5 8 '{"countdownSeconds":3,"audio":{"micEnabled":true},"camera":{"enabled":true}}'
node scripts/bench-flows.mjs src-tauri/binaries/ffprobe-x86_64-pc-windows-msvc.exe
```

`bench-start-stop.mjs` 通过悬浮窗的调试端口点开始、点停止（调试端口只开在本机 127.0.0.1，只对这一个进程生效），所有时间都是网页里同一个时钟记的：

- “倒数结束”＝第一个倒数事件的时间 ＋ 3000 ms；
- “进入录制”＝应用发出 `recording` 状态的时间；
- “存好”＝`stop_recording` 返回文件的时间；
- “丢掉的画面”＝（点停止 − 倒数结束）− 文件时长。

`bench-flows.mjs` 跑暂停／继续、倒数中取消、不倒数三种流程，并用 ffprobe 逐个包检查文件：两路流从哪开始、第一个视频包是不是关键帧、声音里最大的空洞、整段解码有没有错误 `[flows2.json]`。

脚本入库后用同一个发布版又跑了一遍 `[scripts-verify-startstop.txt, scripts-verify-flows.json]`，和上表一致：倒数结束 → 录制中位数 −3 ms，停止 → 存好 289 ms，丢掉的画面 0（文件反而多出约 0.1 秒，是闸门前那一帧）；第一个视频包是关键帧，声音最大空洞 0.021 秒，解码 0 错误。暂停这次是 199 ms（上表 95 ms），单次波动，没有再多跑。

拆分停止耗时用的几个一次性实验脚本（`exit-*.mjs`）没有入库，结论都写在 3.2 里。

## 3. 改了什么，为什么

### 3.1 开始：倒数期间就把设备全打开

旧版：倒数结束后才启动 ffmpeg，再依次打开屏幕、麦克风、摄像头（摄像头 2.8 秒），再初始化编码器。用户看着“1”消失后还要等 2 秒。

新版：

1. 倒数一开始就启动 ffmpeg，三个设备在倒数期间打开。
2. 所有输入按墙上时钟打时间戳（屏幕、摄像头、麦克风共用一个钟），倒数结束的时刻叫“闸门”。
3. 编码器从一开始就在跑；在闸门处强制一个关键帧（IDR），闸门之前的包用 ffmpeg 的 `noise` 过滤器扔掉。倒数结束时编码器已经热了，第一帧在闸门后 13–208 ms 写进文件 `[final-app.log 里的 go.first_frame]`。
4. 倒数窗口和选区轮廓窗口都设成“不被截屏”，不需要先藏窗口再等 150 ms。
5. ffmpeg 打出 `Press [q] to stop` 就说明设备全开了，这是“准备好”的信号。

先试过一个更简单的办法（在编码器前面剪掉闸门之前的帧），实测有问题：编码器在闸门之后才初始化（QSV 0.6–0.9 秒），这段时间 ffmpeg 会压着麦克风不读，声音晚到、被打上晚的时间戳，开头约 0.6 秒的声音丢了 `[A · 手工实验 g1/g2]`。所以改成上面的“先编码、后剪包”。这个办法只用在实测过的编码器上（Intel QSV、Windows 自带的 Media Foundation），别的编码器（NVIDIA、AMD 等，本机没有）退回“编码前剪帧”。

顺带修好的旧问题：旧版每个设备各自从 0 开始计时，谁先打开谁就对不上。录像里画面比声音长 0.9 秒，摄像头的画面比屏幕超前约 2.5 秒（摄像头晚打开）。现在共用一个钟，长度差 0.074 秒。

### 3.2 保存：只等文件，不等设备关完

旧版点停止后，ffmpeg 要 0.6–0.75 秒才退出。拆开看 `[exit-*.mjs 实验]`：

- ffmpeg 默认每 0.5 秒才看一次有没有人按停止，平均白等 0.25 秒。现在改成 0.1 秒（`-stats_period 0.1`）。
- 文件写完以后，ffmpeg 还要再花 0.1 秒（麦克风）到 0.4 秒（摄像头）关设备。现在看到 ffmpeg 报告结束（`progress=end`，这时文件已经关好）就往下走，设备在后台自己关。
- 每次开应用后第一次保存，要等 ffprobe 第一次启动 1.1–1.4 秒（系统要读、要扫这个程序）。现在应用一打开就先跑一次 ffprobe。新版第一次保存 212 ms。

### 3.3 取消倒数

倒数中取消：ffmpeg 立刻结束，状态回到空闲，工作文件夹不留下 `[flows2.json → cancel]`。

## 4. 没做到的

1. **暂停后继续仍要约 1.8 秒**。卡在重新打开摄像头。想做到瞬间继续，只能暂停时不关摄像头和麦克风（指示灯一直亮着），这是隐私上的取舍，要你定。
2. **不倒数直接录仍要约 2 秒**。原因同上：点下去之后设备才开始打开。
3. **上架版：麦克风的权限框没人回答时，现在是直接报“无法开始录制”**，不再像上周那样等 12 秒。我单独在包里跑 ffmpeg，同样打不开麦克风 `[A]`，所以是这台机器的权限状态，不是这次的改动。这种情况更合适的提示是“去设置里允许麦克风”，还没做。
4. **NVIDIA／AMD 显卡没测**（本机没有）。代码对它们走保守的路：开始一样快，但开头可能少约 0.5 秒声音。
5. **暂停过的录像、不倒数直接录的录像，画面仍比声音长约 1 秒**（旧版 0.95 秒，新版 0.93／1.07 秒，`flows-compare.txt`）。这是老问题，这次没碰：这两种情况用的还是旧的启动方式，设备先后打开、各自计时。倒数开始的那一段已经修好（0.074 秒）。要修就得把“共用一个钟”也用到继续和不倒数上，但这次试过：设备在“起点”之后才打开时，ffmpeg 会在开头补一串重复帧，所以先退回了旧方式，需要另想办法。
6. **Mac 上没编译过**。共享代码 `command.rs` 的新参数只在 Windows 屏幕源上生效，`-stats_period 0.1` 和“看到 progress=end 就算结束”对 Mac 的 ffmpeg 路径也生效（Mac 现在主要走原生 helper，不经过 ffmpeg）。

## 5. 架构，以及还能优化的地方

架构一句话：Svelte 界面（主窗口、悬浮条、倒数／选区窗口）→ 带类型的 IPC → Rust 应用层（`commands.rs` 管命令和倒数，`recorder.rs` 管录制状态机、分段和 ffmpeg 进程）→ 纯逻辑核心（`crates/core`：拼 ffmpeg 命令、选编码器、码率预算、崩溃恢复）。Windows 上靠 ffmpeg 录（屏幕 ddagrab，摄像头和麦克风 dshow，Intel QSV 编码），Mac 上靠原生 helper。暂停就切一个新分段，停止时用 `-c copy` 把分段接起来。

还能做的，按收益排：

1. 暂停时不关设备，继续就能瞬间开始（见 4.1，要你定）。
2. 4K 屏幕现在是先把整帧拷回内存再缩小，CPU 要多花一截。上次试显卡直接缩放没成（像素格式不支持），值得再试一次。
3. 停止时还会把整段重新封装一遍（把索引放到文件开头）。5 分钟的录像实测只多花几十毫秒；一小时的录像估计要一秒多，没实测。
4. 上架版里麦克风被拒时，给出“去设置里允许”的提示（见 4.3）。
5. 暂停过的录像和不倒数的录像，画面声音长度差约 1 秒（见 4.5）。
